# Dedicated HARVEST Feedback backend

This backend imports the matching HARVEST Cognito pool and creates no user pool, app client or identity pool. `dev` serves HARVEST prestaging and uses HARVEST staging identity and API. `production` creates a separate Feedback stack for HARVEST production identity and API. The existing Amplify sandbox remains unchanged.

The optional Feedback-to-Linear routing design is in [docs/LINEAR_INTEGRATION.md](../docs/LINEAR_INTEGRATION.md). It stays disabled until the dedicated dev or test secret name is supplied. Production Linear routing is disabled pending separate review and credentials. Synthesis and local tests do not create Linear issues.

Run from the Feedback repository root:

```
npm run integration:typecheck
NODE_OPTIONS=--no-experimental-webstorage npm run test:coverage
node integration-backend/synth.mjs
```

The synthesis command reads the ignored `.env.integration.local` or explicit environment settings, writes `cdk.out`, and asserts the resource boundary. It never deploys. Its offline check passed against the 19 October saved live template. For production synthesis, set `FEEDBACK_TARGET=production`, `HARVEST_PRODUCTION_USER_POOL_ID`, `HARVEST_PRODUCTION_APP_CLIENT_ID`, `HARVEST_PRODUCTION_API_BASE_URL`, `HARVEST_PRODUCTION_DB_HOST`, `HARVEST_PRODUCTION_VPC_ID`, `HARVEST_PRODUCTION_PRIVATE_SUBNET_IDS`, `HARVEST_PRODUCTION_DIRECTORY_SECURITY_GROUP_ID` and `HARVEST_PRODUCTION_AVAILABILITY_ZONES` from the live HARVEST production infrastructure. Run `node integration-backend/verify-production-boundary.mjs` with read-only AWS access before reviewing the production template; it compares these values with the live HARVEST production stack and subnet zones. The backend checks the known production pool, client, API and public site origin before synthesizing. Production email, HARVEST bell delivery and Linear routing are off until their production credentials and endpoints are separately reviewed; never reuse staging secrets. Each resolver independently calls the matching HARVEST `/api/me` with the access token. Any live Operator membership grants Feedback admin access, including HARVEST `user`; Company/Partner membership alone grants client access, regardless of email domain or Cognito groups. All verified Feedback admins see every report; the assignee is a work owner, not a visibility filter. Verify that intended Meridian development and operations accounts have active Operator memberships before release. The old AdminAssignments table is retained to preserve deployed data, but this rule no longer reads it. The currently deployed dev backend still uses selected assignments until this change is reviewed and deployed.

Reporter reads additionally require current membership in the stored organization. Client writes support submission and update requests; server timestamps and optimistic revisions protect changes. There is no generated model CRUD or token-group admin bypass.

Attachment upload/download capabilities expire in 60 seconds. New operations recheck live membership. An already issued URL remains usable for its finite lifetime; do not claim instant revocation of that URL. Atomic claims prevent reuse across reports, and downloads pin the immutable S3 version captured at submission. Versioned storage is retained on stack deletion. Cleanup of orphaned objects is still pending.

The existing Admin selector is retained as a queue identifier (`admin@example.com`); it is not a recipient address. The selector also lists active Operator members by stable subject, with server validation on every assignment.

Email preserves the latest renderer and limits client mail to submission, a server-recorded response to a pending update request, and closure. Routine status changes still produce in-app notifications. In this local change, recipients are live Operator members with enabled, confirmed Cognito identities. A Feedback-owned IAM-only directory uses a dedicated column-scoped database credential, read-only transactions and verified RDS TLS. It never reads the HARVEST master database secret. The query does not read `memberships.role`; verify the existing directory credential and column grants before deployment. Applying `node integration-backend/provision-directory.mjs .integration-outputs.json --profile harvest-dev --apply`, if needed, changes database access and requires separate approval. No HARVEST API code deployment or security-group modification is needed.

Email starts disabled. Its receipts, retry lease and failure queue are ready; enable only after the directory and SES identities are checked in the matching environment. The integration records updateRespondedAt only for an authorized admin saving a pending request; the UI labels this action Send update. Clients cannot set that server-owned event.

HARVEST bell delivery uses a separate Reports stream worker for new client reports and update requests. It posts only event ID, report ID, company and title to HARVEST's signed `/api/comms/feedback/events` endpoint. The staging HARVEST stack must first create `harvest-refresh/staging/feedback-notifications` and deploy migration `0215_feedback_notifications.sql`; the Feedback worker receives a read grant for that secret. The endpoint records an idempotency receipt and writes to the existing operator notifications table in one transaction. The worker retries failures and retains failed batches in `HarvestNotificationFailureQueue`. Deploy the HARVEST PR to prestaging before deploying this Feedback dev backend change; source pushes alone do not publish the worker.

The private static bucket and CloudFront origin serve only `/feedback` and its assets. `prepare-release.mjs` builds from verified stack outputs and prepares the upload package. Its target-specific settings file supplies `VITE_FEEDBACK_GRAPHQL_URL` and `FEEDBACK_RELEASE_MANIFEST` for the matching HARVEST site. The manifest binds the Feedback target, Cognito identity, endpoint and static origin. Netlify's HARVEST headers do not apply to proxied responses, so the static origin supplies its own CSP, including blob media previews.
